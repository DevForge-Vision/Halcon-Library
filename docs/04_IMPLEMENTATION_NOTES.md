### 2.1 왜 OpenCV 를 쓰지 않았나

Phase 1 다섯 종은 **OpenCV 를 쓰면 오히려 값이 틀린다.**

| OpenCV 함수 | 왜 못 쓰는가 |
|---|---|
| `cv::arcLength` | **근사 폴리곤 길이**다. HALCON 의 "축평행 1 / 대각 √2" 체인 정의(정의서 §2.3)와 불일치 |
| `cv::contourArea` | **폴리곤 면적**이다. CV-1 결론(hull 픽셀 개수)과 불일치. 정사각형에서 `Convexity = 1.0203` 이 되어 Assertion 위반 |
| `cv::findContours` | 반환 좌표가 근사 폴리곤이라 체인 스텝을 셀 수 없음 |

결과적으로 Phase 1 은 **외부 의존성이 0** 이다. 어떤 컴파일러에서도 빌드·검증되고,
사용처의 OpenCV 버전과 충돌할 여지가 없다.

### 2.2 성능 설계

- `area_center` 는 **O(런 수)**. 열 좌표 합을 등차수열 합 `(colBegin+colEnd)·개수/2` 로 상수시간 처리.
  픽셀 순회(O(면적)) 대비 두 자릿수 빠르다.
- `FeatureContext` 가 area/center · contour · convexHull 을 **처음 요청될 때 1회만** 계산하고 캐시한다.

> ⚠ **캐시의 유효 범위 — 오해하기 쉬운 지점**
>
> 이 캐시는 **`FeatureContext` 인스턴스 하나 안에서만** 유효하다.
> 개별 오퍼레이터(`ContLength` / `Circularity` / `Compactness` / `Convexity`)는 **호출할 때마다
> `FeatureContext` 를 스택에 새로 만들고 버린다.** 그러므로
> `Circularity` 와 `Compactness` 를 연달아 호출하면 **윤곽 추적이 두 번 일어난다.**
> (이 문서의 이전 판은 "한 번만 만든다" 라고 서술했다. 사실이 아니었으므로 바로잡는다.)
>
> 중복을 없애려면 배치 API 를 쓴다.
>
> ```cpp
> RegionFeatures f;
> ComputeFeatures(region, f);		// FeatureContext 1개를 5종이 공유한다
> ```
>
> | 호출 방식 | 윤곽 추적 | convex hull |
> |---|---|---|
> | 개별 5종을 각각 호출 | **4회** | 1회 |
> | `ComputeFeatures` 1회 | **1회** | 1회 |
>
> 값은 두 경로가 완전히 같다. `Operators.cpp` 의 익명 네임스페이스에 있는 값 계산 헬퍼 5종
> (`ComputeAreaCenterValue` · `ComputeContLengthValue` · `ComputeCircularityValue` ·
> `ComputeCompactnessValue` · `ComputeConvexityValue`) 을 **양쪽이 똑같이 호출**하기 때문이다.
> 계산식을 두 벌로 복제하지 않았으므로 두 경로가 어긋날 여지가 구조적으로 없다.

- **윤곽 계열은 라벨 이미지를 만들지 않는다.** `Contour.cpp` 는 런 조회 인덱스(행 이진탐색 +
  행 내 런 이진탐색)로 멤버십을 판정한다. 메모리는 **O(런 수)** 이며 바운딩박스 크기와 무관하다.
  대가로 멤버십 판정이 O(1) 에서 **O(log n)** 이 됐다. 의도한 교환이다
  (풀프레임을 가로지르는 가는 스크래치에서 dense 라벨 이미지는 1 GB 를 넘었다).

### 2.3 방어 설계

- 공개 API 밖으로 **예외를 던지지 않는다.** 내부 `try-catch` → 빈 리전 규약(`0` 반환)으로 축약.
- 빈 리전 · 단일 픽셀 · 1픽셀 두께 · 빈 컨투어 · `max == 0` 전부 가드.
- **`Convexity` 에 1.0 클램프를 일부러 넣지 않았다.**
  클램프하면 `F_c` 를 폴리곤 면적으로 잘못 계산했을 때(1.0203) 1.0 으로 덮여
  **CV-1 회귀를 영원히 감지할 수 없기 때문**이다. Assertion 검사(T-6)가 이를 잡는다.

## 3. ⚠ 가장 중요한 교훈 — 곡선 도형의 기댓값을 연속 기하로 잡으면 안 된다

`docs/03_VERIFICATION.md` 초판은 링(S3)의 `ContLength` 기댓값을 **`2πR = 314.16`** 으로 잡았다.
**이것은 틀렸다.** 실측은 **`329.71`** 이고, 구현이 옳다.

### 원인 — 디지털 원의 체인코드 편향

반지름 `R` 인 디지털 원의 8-연결 체인 길이는 연속 원주보다 **약 +5.5% 크다.**
이것은 오차가 아니라 **이산 기하의 성질**이다.

1/8 옥탄트(45°)에서 체인은 축평행 스텝과 대각 스텝으로만 이동한다.

```
옥탄트 1개당 이동량 :  축평행 0.414R × 1  +  대각 0.414R × √2  =  0.828R
전체 8 옥탄트       :  8 × 0.828R  =  6.63R
연속 원주           :  2πR         =  6.283R

비율 = 6.63 / 6.283 ≈ 1.055     → +5.5%
```

R = 50 을 넣으면 `6.63 × 50 = 331.4`, 실측 `329.71` 과 부합한다.

### 이 편향의 파급

| 값 | 영향 |
|---|---|
| `compactness` | `L²` 이므로 편향이 **제곱으로 증폭**된다. S2 원판이 `1.0` 이 아니라 **`1.1027`** 이 나온다 |
| `circularity` | 영향 없음 (L 을 안 쓴다). 다만 디지털 원판의 실제 면적이 7854 가 아니라 **7845** 라 `0.9989` 로 클리핑이 발동하지 않는다 |
| `convexity` | 영향 없음 |

### 규칙 (앞으로 모든 오퍼레이터에 적용)

> **곡선 도형의 기댓값은 연속 기하 공식으로 잡지 말고,
> 이산 정의를 그대로 적용한 값으로 잡는다.**
>
> 연속 기하값은 **참고(NOTE)** 로만 남기고, PASS/FAIL 판정에 쓰지 않는다.
> 대신 **판별력이 확실한 이산 도형**(정사각형·직선·단일픽셀)으로 판정한다.

테스트는 이 규칙에 따라 두 층으로 나눴다.

- **HARD 검사**: 이산 도형의 정확값 대조 + 방향성 판별(예: `S3 ContLength < 400` — 구멍 제외 확인)
- **NOTE**: 연속 기하 대비 편차 기록. 실패로 치지 않는다

| # | 항목 | 초판(연속 기하) | 실측(이산 정의) | 사유 |

| 4 | S2 원판 `Circularity` | 1.0 (클리핑 발동) | **0.99886** | 디지털 원판 면적이 7854 가 아니라 7845 → 클리핑 미발동 |

### 4-1 의 파생 — 클리핑 검증 도형이 없다

초판은 S2 원판이 `min` 클리핑을 발동시킬 것으로 봤으나, 실제로는 발동하지 않는다.
즉 **S1~S7 중 함정 #1(`circularity` 의 `min` 클리핑)을 실제로 트리거하는 도형이 없다.**

대신 **T-6 Assertion 검사**를 추가했다 — 7개 도형 × 4개 Assertion = 28건.

```
0 <= Circularity <= 1
Compactness >= 1  또는  == 0
Convexity <= 1                 ← CV-1 회귀 감지
ContLength >= 0
```

클리핑 방향을 반대로 짜거나(함정 #1·#2), `convexity` 분자/분모를 뒤집거나(함정 #3),
`F_c` 를 폴리곤 면적으로 계산하면(CV-1) 이 검사에서 즉시 걸린다.

### 9.1 §3 규칙을 모멘트에 적용할 때의 재검토

§3 은 "곡선 도형의 기댓값을 연속 기하로 잡지 마라" 는 규칙이다. 모멘트에도 그대로 적용했지만,
**편향의 성질이 다르다는 점은 짚어 둔다.**

| | `contlength` | 2차 모멘트 |
|---|---|---|
| 값의 정체 | **경로 길이** (8-연결 체인) | **픽셀 좌표의 합** |
| 편향의 원인 | 대각 스텝을 `√2` 로 세는 이산 경로의 성질 | 디지털 도형이 연속 도형과 픽셀 몇 개 다른가 |
| `R=50` 에서의 크기 | **+5.5%** | 면적 기준 **0.11%** (7845 vs 7853.98) |

즉 모멘트의 곡선 오차는 체인 오차보다 **두 자릿수 작다.** 그럼에도 `±2~3%` 를 유지했다.
이유는 정확도가 아니라 **원칙**이다 — "곡선 도형은 판정에 쓰지 않는다" 를 한 번 예외로 무너뜨리면
다음 배치에서 반드시 사고가 난다. PASS/FAIL 판정은 전부 **이산 도형**이 담당한다.

### 9.2 판별 도형 3종을 추가한 이유

**기준 도형 S1~S7 은 전부 대칭 도형이다.** S5 L자조차 반대각선 `c = 99 − r` 에 대해 대칭이다
(`(r,c) → (99−c, 99−r)` 가 좌팔과 하팔을 맞바꾼다). 그 결과:

- 최원 윤곽점이 항상 **동률**이라 `orientation_region` 의 `+π` 분기를 판정할 수 없다
- 크기가 다른 같은 도형 쌍이 없어 **스케일 불변성**을 판정할 수 없다
- `Phi = −π/2` 로 떨어지는 도형이 없어 `EA-2` 를 판정할 수 없다

그래서 **S1b**(50×50 정사각형) · **S4T**(세로선) · **S8**(비대칭 아령)을 추가했다.
S8 은 두 정사각형의 **크기를 다르게** 대각 배치해 최원점이 `(0,0)` 하나로 유일해지도록 설계했고,
좌표를 골라 `Ra = 41`, `Ia = 210125`, `Ib = 14125` 가 **정확한 정수**로 떨어지게 했다.

### 9.3 원문의 결함을 해소한 3건 (수식을 그대로 옮기면 안 되는 지점)

| # | 원문 | 문제 | 처리 |
|---|---|---|---|
| 1 | `Ia = h + sqrt(h² − M20·M02 + M11²)` | `M20 ≈ M02` 에서 큰 두 수의 차 → 자리수 소멸. 대면적에서 `h² ≈ 1e35`. 부동소수 오차로 **음수 → NaN** | 항등 변형 `sqrt(((M20−M02)/2)² + M11²)` 로 구현. **값은 대수적으로 동일**하고 원리적으로 비음이다 |
| 2 | `elliptic_axis` 의 "normalized and passed to the area" | `F` 인지 `F²` 인지 불명. 옆 오퍼레이터(`_invar`)가 `F²` 라 혼동 위험이 크다 | 연속 원판에서 `Ra = R` 이 성립하는 유일한 값이 `F` — 원문 논리로 확정 (`EA-1`) |
| 3 | `eccentricity` Assertion `Anisometry >= 1.0` vs Attention "anisometry of 0" | 문서 자기모순 | **Attention(실제 동작 0)을 따른다.** Assertion 쪽을 따르면 1픽셀 스크래치가 "완전한 원" 이 된다 |

### 9.4 원시 모멘트를 그대로 모으면 안 된다 (실무 사고 지점)

`SUM c²` 를 모아 `mu02 = SUM c² − (SUM c)²/F` 로 빼는 교과서 방식은
**바타입 급 이미지에서 유효자리가 날아간다.**

```
53580 열 이미지의 작은 blob (폭 10픽셀, 100 px)
    SUM c^2  ~ 100 x 53580^2 ~ 2.9e11
    mu02     ~ 8.3e2
→ 1e-9 규모의 상대 차이를 double 로 뽑아내야 한다
```

그래서 **무게중심에 가장 가까운 격자점으로 좌표를 먼저 옮긴다.** 남는 소수부는 `|f| <= 0.5` 뿐이다.
이 시프트가 없으면 검사기 실사용 좌표에서 조용히 값이 흔들린다
(기준 도형은 좌표가 0~120 이라 **이 문제를 잡아내지 못한다** — 테스트가 통과해도 안심할 수 없는 지점이다).

### 9.5 구조 등식으로 잡는 회귀 (T-12)

기댓값 표만으로는 "한 오퍼레이터만 고치고 나머지를 안 고친" 회귀를 못 잡는다.
도형과 무관하게 항상 성립하는 등식 7종을 테스트에 넣었다. 그중 두 개가 결정적이다.

```
I-1 : M**_invar · F^2  ==  M**            §6 ↔ §7 정규화 연쇄
I-2 : Ra == 2·sqrt(Ia/F) , Rb == 2·sqrt(Ib/F)   §6 ↔ §8 정규화 연쇄 (EA-1)
```

**`I-2` 가 가장 중요하다.** `elliptic_axis` 의 정규화를 잘못 넣으면 `Ra` 가 `sqrt(F)` 배 어긋나는데,
`Phi` 도 `Anisometry` 도 정규화에 둔감해서 못 잡는다. 잡아 주는 것은 정확값 표와 `I-2` 뿐이다.

### 9.6 미해결 (HALCON 실측 1회로 전부 해소된다)

| ID | 내용 | 잠정 | 판정 도형 | 스위치 |
|---|---|---|---|---|
| `MI-1` | `_invar` 의 원점이 무게중심인가 | 무게중심 | **S5** | `GLIM_HALCON_INVAR_ORIGIN_BBOX` (0) |
| `EA-2` | `Phi = −π/2` 를 `+π/2` 로 접는가 | 접는다 | **S4T** | `GLIM_HALCON_PHI_FOLD_HALF_PI` (1) |
| `EC-1` | `Rb=0` 의 `StructureFactor` 가 `−1` 인가 `0` 인가 | `−1` | **S4 / S6** | `GLIM_HALCON_STRUCTURE_FACTOR_ZERO_ON_RB0` (0) |
| `OR-2` | `+π` 후 `[−π, π)` 로 접는가 | 접는다 | (범위 문제) | `GLIM_HALCON_ORIENTATION_WRAP` (1) |
| `OR-3` | 최원점 동률(대칭 도형) | **판정 불가** | — | 순회 순서 고정 |

`EC-1` 의 기본값을 `−1` 로 둔 것은 §2.3 과 같은 판단이다.
**틀렸을 때 `−1` 은 눈에 띄고 `0` 은 빈 리전 규약에 묻혀 영원히 안 보인다.**

확장 시에도 §3 의 규칙(**곡선 도형 기댓값을 연속 기하로 잡지 말 것**)을 반드시 적용한다.
